# Deep Proof

Evidence-led review workspace. Deep Proof reviews project dossiers with Analyst Skills, ties every assertion to an exact source quotation, and labels each report with the verification status of the skill that produced it. All AI work runs through [ALA (Advanced Language Agent)](https://github.com/AssistOS-AI/AdvancedLanguageAgent); Deep Proof never calls Codex, Claude Code, OpenCode or Pi directly. No formalization cache, Datalog or neurosymbolic engine is included.

## Install

Requires Node.js 24 or newer (built-in SQLite), Python 3, Poppler (`pdftotext`), LibreOffice (`soffice`), Bubblewrap (`bwrap`) and Chromium for PDF export.

Deep Proof looks for ALA in the **parent folder** of the application by default, so the recommended layout places both checkouts side by side:

```text
workspace/
├── AdvancedLanguageAgent/        # ALA
└── deep-proof-community-edition/ # Deep Proof
```

```sh
cd workspace
git clone https://github.com/AssistOS-AI/AdvancedLanguageAgent.git
cd AdvancedLanguageAgent && npm install && cd ..
cd deep-proof-community-edition
npm start
```

ALA also needs Bubblewrap and at least one installed, authenticated coding agent: Codex, Claude Code, OpenCode or Pi. `npm install` in the ALA folder installs its AchillesAgentLib dependency (`ploinky-agent-lib`); with a local checkout you can instead run `npm install --no-save --package-lock=false /path/to/AchillesAgentLib`.

Open http://127.0.0.1:8000. Initial credentials are **admin / admin**. Administrators change any user’s password in Administration → Users & Access, including their own. A new installation starts empty: initialization creates only the administrator account, with no demo projects or Analyst Skills. Each organization creates its own projects and adds or imports its own skills. Subsequent starts preserve the database and never reset passwords.

`PORT` and `HOST` override the listening address. `ANALYST_DATA_DIR` overrides `.runtime/`, which contains the SQLite database and isolated AI job folders. Back up this directory; keep it out of source control. When serving through HTTPS, set `ANALYST_SECURE_COOKIE=1`. The application defaults to localhost.

### Locating ALA

ALA is resolved in this order:

| Order | Source | Behaviour |
| --- | --- | --- |
| 1 | `ALA_CLI` environment variable | Operator override; points to `bin/ala.mjs` or the ALA folder. |
| 2 | Saved location | Set in Administration → Deep Proof Configuration. An invalid saved location is reported, never silently replaced. |
| 3 | Parent folder | `../AdvancedLanguageAgent`. When found at startup and no location is saved, Deep Proof saves it automatically. |
| 4 | Application folder, then `PATH` | `./AdvancedLanguageAgent`, then an `ala` executable on `PATH`. |

A location is accepted only when it contains `bin/ala.mjs`, `src/coding-agents/discovery.mjs` and a `package.json` named `advanced-language-agent`. The startup log prints the resolved entrypoint or the locations checked. If ALA is not found, administrators see an alert on every page and are taken to **Deep Proof Configuration** on first use to enter the absolute path, for example `/home/me/work/hot/AdvancedLanguageAgent`. **Use Automatic Detection** clears the saved path. New reviews and skill generation are refused with a clear message while ALA is unavailable.

## Editions

Deep Proof shows **Community Edition** next to the logo by default. When a folder named `commercial-license/` exists in the application root, the badge is hidden; place the commercial license agreement inside it. The check runs on each page load, so no restart is needed.

## Analyst Skill Verification

An Analyst Skill that has not been validated is not safe for real-world problems without rigorous validation. Every Analyst Skill is **Use With Caution** until it is evaluated scientifically and certified. A skill becomes **Verified** only when its saved revision contains a valid `verification-certificate.md` at the skill root, which is possible only by importing a package that includes it.

Skills generated by Deep Proof and imported packages without a certificate are Use With Caution; a certificate found in a generated package is discarded, because an AI creator cannot certify its own work. Saving changes to Review Criteria, Review Playbook or Report Template, changing reference files or regenerating creates a Use With Caution revision; renaming keeps verification. A malformed certificate makes the import fail.

The status is fixed in each analysis snapshot when the run starts. Reports from Use With Caution skills are labelled USE WITH CAUTION in the reader, the analysis history, the PDF header, on every PDF page (with a watermark) and in the PDF filename. Verified reports show who certified the skill, when and on how many evaluation cases. Analyses created before this feature carry no verification record and are shown as Use With Caution.

The full standard, including why unverified skills cause harm, how to evaluate a skill and the certificate format, is in [docs/skill-verification.md](docs/skill-verification.md) and in the application under **Documentation**. Deep Proof checks the certificate's structure; the truth of the attestation is the responsibility of the reviewer named in it.

## Administration

The default analysis backend is **Codex with `gpt-6-luna`**, invoked through the local ALA checkout.

Administrators can add, edit and delete users, reset passwords, disable accounts and assign allowed analyst skills. Administrators see all projects and skills. New projects belong to their creator and are initially shared with their Primary Access Level. Each review explicitly selects an allowed, ready Analyst Skill. When no Analyst Skill is ready, New Analysis offers administrators a direct path to create or import one, explains its Use With Caution limitations and supports exploratory testing after the rules are ready. Users without administration rights are directed to request access. Existing project audiences are migrated to explicit user grants. Access checks apply to each project, document and historical report endpoint. Role, access and password resets invalidate the affected user's sessions. At least one active administrator must remain.

Projects require only a project name. Choose an Analyst Skill when starting each review; different reviews of the same project may use different skills. The report history displays the snapshotted skill name. Administrators can use Delete project in the project header. After confirmation, the project, documents, saved analyses, evidence snapshots and associated AI job folders are permanently removed; the analyst skill and its review rules remain. Deletion is blocked while an analysis is running. Administrators can also archive and restore projects. Archive moves them out of the active list into the separate Archive area, preserving documents and reports. Both lists and all direct document/report URLs enforce project access. Archived projects are read-only until restored. Existing databases are migrated automatically to add the archive timestamp.

Analyst Skills can be deleted when no review or generation is using them. Saved reports retain their skill snapshot. Create a skill with its name, instructions and any number of reference files. Files are uploaded individually (20 MB per file), so there is no fixed file-count limit. Supported references: PDF, DOC, DOCX, PPT, PPTX, TXT and Markdown. The named skill is saved before uploads and generation; failed uploads can be retried from its editor. The application stores originals, extracted text and Office PDF previews under `.runtime/project-types/<type-id>/attachments/`.

**Reference Files** in the full-page editor lets administrators inspect, add, replace or remove attachments and regenerate the methodology. Changes mark the skill as needing regeneration; analyses cannot start with outdated methodology. Reference mutation is blocked during generation so the generation input remains stable. **Review Criteria**, **Review Playbook** and **Report Template** remain manually editable. Saving them creates a new skill revision with those files as the authoritative rules. Previous analyses keep their original rules and skill snapshots.

Generation creates a complete package under `.runtime/analysis-skills/<type-id>/revisions/<revision>/`: `SKILL.md`, criteria, playbook, detailed methodology, a source-coverage map, source extracts and domain-specific helper scripts. The design validator checks required files, coverage/line ranges for every reference and Node/Python script syntax. Generated scripts are never executed by the web server; the agent is instructed to test them within its sandbox. Structural validation does not prove semantic correctness. Every analysis copies the selected immutable revision into `skills/analysis-type-<id>/` alongside the standard evidence, reporting and progress skills. Existing skills are packaged from their saved rules on migration without an AI call; regenerate them to obtain the expanded AI-designed methods and code.

The **Skill Files** tab provides a read-only view of the saved package. **Report Template** edits its Markdown chapters and guidance.

**Import analyst skill** accepts a ZIP with exactly one `SKILL.md`, either at the archive root or inside a single enclosing folder, and its readable text/code resources. Import requires no model call. Unsafe paths, links, duplicate entries, encrypted archives and extraction bombs are rejected. ZIPs are limited to 20 MB compressed, 100 MB expanded and 2,000 archive entries; generated supporting files are limited to 2 MB each (source extracts up to 10 MB). Binary assets are not supported in this import format. Existing criteria/playbook files are preserved. Import requires explicit criteria, playbook, methodology and report template files; incomplete packages are rejected. See the [external skill creator contract](skills/review-design/references/import-contract.md), which is also used by the integrated creator.

Administration has separate **Users & Access**, **Access Levels**, **Analyst Skills**, and **Deep Proof Configuration** tabs. Generation continues if the browser closes; interrupted server runs are marked for retry.

Project document uploads also support selecting multiple files at once, with a 20 MB limit per file, individual progress and retry of failed files. Single uploads retain an editable title, and pasted document text remains supported.

## Report Import and Quality Checks

Use **Import Report** in a project to upload an external report (PDF, Word, PowerPoint, Markdown or text, up to 20 MB). Imported reports appear in the same report history and reader as generated reports. Deep Proof preserves the original file for download and displays the extracted text without requiring its own chapter or citation format. Multiple files can be selected together; each file becomes a separate report with its filename as the title. Failed uploads can be retried without duplicating successful ones. Import does not call a model or validate the report's claims; scanned files without extractable text need OCR before import.

Open a completed report and choose **Check Report** to create a separate, adversarial quality assessment. It always uses the built-in **Rigorous Report Verification** procedure, which looks for what the report missed, treated superficially, got wrong or contradicts in its own sources; it does not have to be exhaustive. The dialog asks only for Report Language (defaulting to the report's own language), Verification Depth and Research Mode, with no open questions. Each check runs through the usual ALA job and validated output workflow. Every check of a report is kept: the report's **Quality Checks** entry lists them newest first, with depth, research mode, outcome and the confirmed findings by severity, each linking to its full check report. The original report and its verification status remain unchanged.

Checks of generated reports use their saved evidence and original criteria, preserving the historical context. Checks of imported reports capture the project's current source documents; they can also run with only the imported report, in which case factual accuracy must be reported as unverified where underlying evidence is unavailable. Add underlying evidence to the project's documents before checking an imported report. Archived projects must be restored before importing or starting a check.

The self-contained procedure lives in [skills/report-quality/SKILL.md](skills/report-quality/SKILL.md), implementing specification 1.0 dated 2026-10-29. It packages the common mandate/evidence/omission/challenge protocol, ten combinable domain profiles, F01–F12 defect taxonomy, machine-readable contracts, a report template, examples, source/segment preparation, a standalone validator and a Python Decimal arithmetic helper. It uses only Node/Python standard libraries. The complete bundle is hashed and snapshotted for each built-in check; future edits do not rewrite saved methods or reports.

Built-in checks default to deep, closed-dossier verification. Each run can select explicitly labelled triage or a historical reference date, or authorize public external research without disclosure of confidential dossier contents. External evidence is retained separately and is forbidden in closed mode. Each candidate is challenged; confirmed findings require criterion, evidence, executed check, alternative-explanation result, impact, remedy and closure. Major/critical findings require a distinct original-evidence revisit. Zero confirmed findings and explicitly incomplete reviews are valid outcomes; neither constitutes universal assurance.

Each built-in check runs in a private operating-system temporary folder. Source snapshots and original files are copied there; progress is mirrored to the existing project stream. Only validated narrative, registers, evidence inventory and referenced check artifacts are published back, then the temporary folder is removed on success or failure. **Download Verification Records** exports the retained artifacts and hashes. Access checks apply to the bundle and individual artifact links, and changed saved artifacts are rejected. The source report remains intact.

Standalone use: `node /path/to/report-quality/scripts/prepare.mjs /path/to/input.json` creates and prints a temporary workspace. Follow the skill there and run `node /path/to/report-quality/scripts/validate.mjs WORKSPACE`. Preserve output before cleaning the standalone workspace. Deep Proof additionally validates the narrative contract. Other imported Analyst Skills keep their existing output contracts; the rigorous registers are required for the versioned built-in verification skill.

This skill is **Use With Caution** and **is not safe for real-world problems without rigorous validation**. Proposed precision/recall targets are not measured performance. Structural validation verifies data shape, references, exact source quotations, numerical replay and declared coverage consistency; it cannot certify semantic truth, truthful descriptions of visual inspections or exhaustive detection. The independent [evaluation plan](tests/evaluation/report-quality/README.md) stays outside the runtime package and no evaluation answer keys are sent to the agent.

Failed analyses display a plain-language explanation distinguishing engine configuration, service access, execution time, failed result validation, interruption and unexpected execution/storage issues. They explain that no validated report was published and suggest an appropriate next step; raw engine diagnostics are not sent to readers.

## ALA integration

Administration → Deep Proof Configuration shows the ALA status and location, followed by two selectors: Agent and Model. Agent discovery and supported model identifiers come dynamically from ALA’s coding-agent discovery/service modules, using the same ALA installation resolved as described in Locating ALA. Only installed agents and models reported for that agent can be saved. Agent Default leaves the model choice to the native CLI. Saving stores only the selected agent/model and clears old effort overrides. Existing running jobs retain their settings snapshot. Catalog loading is lazy, cached for one minute, bounded by a timeout, and can be refreshed with Retry Catalog. Failures do not overwrite the saved configuration. Listing uses native catalog protocols and never sends a prompt or starts inference. Offline tests inject hand-authored catalog metadata and never query model providers.

Each task receives its own writable job directory containing `input.json`, copied analysis skills, prompt and a per-task ALA config. The application database and other project directories are not mounted as task folders. The standalone ALA child process excludes inherited `PLOINKY_*` variables: it uses the native coding-agent login, not a Ploinky router. This prevents unrelated host router credentials from triggering incomplete generated-local router configuration. The ALA process has a 15-minute deadline; at most two AI jobs run simultaneously. Analysis returns a job ID immediately, and the browser receives progress and completion through SSE without page refreshes. Runs interrupted by a server restart are marked failed. Failed or structurally invalid output is never presented as a completed report.

The integration uses `--ca`, `--cwd`, `--config`, `--taskFile` and `--output`, plus session-free `--control-stdin` for analysis progress (requires the updated local ALA checkout). ALA owns coding-agent sandboxing and authentication. Its full-access default applies inside its sandbox. Deep Proof prompts require supplied-document-only review; ALA's backend may still expose web tools. This instruction is not a network sandbox guarantee.

Text size controls in the header use one CSS scale variable, with the chosen size saved in the browser. New reports prohibit bullet/numbered lists and use grouped, prioritized tables and cited overview charts where meaningful. Existing saved reports retain their content.

## Project Access

Administration → **Access Levels** starts with **High Confidential**, **Normal** and **Everyone**. New users receive Everyone if that default level still exists. Administrators assign multiple levels and a Primary Access Level in the user editor. New projects inherit only the creator's primary level. If the user has no levels, the project initially remains accessible to its owner and administrators (plus any global-access members).

The owner or an administrator opens **Project Access** to select levels and individual users. A match with any selected level or direct assignment grants dossier access; it is not an intersection or a classification hierarchy. Everyone and Normal can be removed from a project. **High Confidential** is the deliberate exception: its members can access every project while that level exists. Ownership and administrator access are always retained. Project access permits reading documents/reports, adding evidence and starting reviews with allowed skills. Only the owner/admin can change sharing; archive/delete remains admin-only.

Every level can be renamed or deleted, including Everyone and High Confidential. Renaming preserves the level's default/global behavior; deleting removes memberships and project assignments, including its global access. Deleted defaults are never recreated on restart. Recreating a level with the same name creates an ordinary new level without special privileges. Other membership or individual grants remain valid. If a primary level is deleted, a remaining membership becomes primary, or none if there are no memberships. Disabled accounts cannot sign in. Deleting an owner is blocked while they own projects; disabling the account preserves its dossiers.

Existing project audiences are migrated once to individual grants without making those projects public to Everyone. Skill permissions no longer determine project visibility. API, document, PDF, report and live progress routes all enforce the same project access policy.

## Report contract

Each skill defines its chapters in `references/report-template.md`. Level-two headings give the chapter order; optional `<!-- section: ID -->` markers provide stable identifiers. Exactly one chapter has `<!-- role: criteria -->`. Each review snapshots this template as `report-template.md` and in its metadata; the UI and validator use that structure. Legacy reports retain the historical template from `src/default-report-template.md`.

The primary output is `report.md`, with evidence footnotes for each substantive assertion, confidence and uncertainty. Footnotes identify the source, inclusive line numbers and exact quote. Criterion assessments also include the criterion and a status. Server validation checks section coverage, criterion coverage, source existence, line bounds and quote matches. It cannot prove that a source logically supports an assertion; relevance remains subject to reviewer judgment.

Citation buttons open rendered Markdown evidence with highlighted passages. Download PDF exports the report with charts and an evidence appendix. Chromium is required for export. Reports are saved under `.runtime/projects/<project-id>/analyses/<analysis-id>/report.md`, alongside source snapshots, rules, charts and their cited CSV data. Project input files are kept in `.runtime/projects/<project-id>/documents/`. SQLite indexes projects, access and run status. Existing JSON reports are migrated to Markdown.

PDF, DOC, DOCX, PPT, PPTX, TXT and Markdown uploads are supported up to 20 MB, with a 2-million-character extraction limit. PDF uses the native browser viewer; Word and PowerPoint are converted to PDF with LibreOffice (`soffice`, override via `LIBREOFFICE`). Text extraction requires Poppler (`pdftotext`), and Office package extraction requires Python 3. Conversion runs inside Bubblewrap (`bwrap`) with no network and access only to runtime libraries, fonts and its temporary folder. At most two documents convert concurrently. Scanned-only project evidence needs OCR before upload. Image-only type reference PDFs are retained with an explicit visual-review requirement; AI is instructed to inspect the original rather than infer missing content. PowerPoint extraction includes speaker notes and hidden slides; Office extraction also preserves additional document text and available cached chart/workbook values. The original document and extracted text are preserved. The viewer offers Document and Text views for PDF/Word/PowerPoint.

The agent writes complete Markdown files, runs the supplied validator, and repairs errors before returning. The server validates independently and can request up to three attempts within one shared deadline. A report check offers a **Time Limit** of 10, 15, 20, 35, 60 or 90 minutes in its dialog (35 for Deep, 15 for Triage unless you choose otherwise). An analysis uses the **Analysis Time Limit** set by an administrator in Configuration → Diagnostics (30, 60, 90, 120 or 240 minutes; 60 by default), frozen with the run when it starts. The chosen limit is the total: the last part of it (15%, between 1 and 5 minutes) is reserved so the agent can write up what it verified in one resumed turn. If that still does not validate, Deep Proof publishes the reviewer's own progress notes. Reaching the limit is a state, **Time Limit Reached**, not an error: the page says it is not a validated report, contains no findings or citations when only notes exist, and says plainly when the reviewer noted nothing in the allotted time. Runs stored as failed by the earlier fixed 15-minute limit are converted to this state at startup with their last saved note. Skill generation keeps a fixed 15-minute limit. A running analysis shows how long it has been running (and its limit); the limits live in `src/run-limits.mjs`, and `DEEP_PROOF_WORK_MS` / `DEEP_PROOF_WRAPUP_MS` override them for testing. It never parses the truncated final chat as the report. Failed validation is shown with a concise user message; technical details remain in local run artifacts.

`skills/review-progress/SKILL.md` instructs the agent to maintain concise, source-grounded updates in `progress.md` during work and repair cycles. After 60 seconds without changed progress, the host sends a live reminder in the same execution. Only one reminder may await acknowledgement; queued or rejected delivery disables further reminders to avoid accumulating extra turns. Native operations may delay the actual update until the agent regains control. Reminders stop on completion, child exit or timeout. The authenticated SSE endpoint sends the latest update, rechecks visibility, and closes on completion or lost access. It does not expose raw execution logs.

Task methodology lives in `skills/evidence-review/SKILL.md` and `skills/review-design/SKILL.md`. ALA receives these files from Deep Proof rather than discovering them itself.

## Security and operational boundaries

Artifact reads reject traversal, symbolic links, hard links and oversized files. Chart CSV data is checked with the same rules as report files. PDF exports render in a private server-owned temporary folder, with a two-export concurrency limit; the cache fingerprint includes the rendered text and chart content. Server errors return a reference code rather than internal paths or execution logs. Saved report API responses exclude engine settings and internal generation inputs.

Sessions are rechecked after request-body reads, document conversion and PDF export. Project access checks apply to original files, previews, reports and SSE; skill grants govern new review selection. This is a local application review with regression tests, not a penetration-test certification. The actual ALA/coding-agent authentication and sandbox are separate runtime boundaries. The review does not run or certify a new live model response.

## Verification

```sh
npm test
npm run check
```

These default commands run small local tests only: authentication, authorization, passwords, administration, archived analyses and report/citation validation. They do not call ALA or any LLM. The report fixture in `tests/fixtures/revenue-review.json` contains the input and actual output of a successful ALA → Codex → `gpt-6-luna` run captured on 2026-10-07. Tests reuse it without regenerating it or simulating an AI agent. Security regression tests cover artifact traversal and links, active SVG rejection, revoked sessions, malformed request bodies, split UTF-8 input and private report metadata.

Optional browser checks are separate:

```sh
npm run test:browser
```

Chromium is required (default `/usr/bin/chromium-browser`, override with `CHROMIUM`). Browser screenshots are written to `/tmp/deep-proof-{home,admin}.png`.

Live model tests must run **only when explicitly requested by the user**:

```sh
npm run test:llm
```

This command consumes model usage and uses the actual local ALA checkout, Codex and `gpt-6-luna`. It retains its input and validated report in the printed temporary job directory. It is excluded from `npm test` and `npm run check`. Fixtures are never refreshed automatically. ALA or model failures are reported as failures.


## Report Language and presentation

Each analysis run selects its own Report Language in New Analysis (English by default). Language is not a skill or global setting. A new analysis snapshots this selection and instructs the engine to use it for prose, headings, tables, charts and progress; exact source quotations remain unchanged. Saved analyses retain their original language. Translated headings use stable section and criterion markers so validation does not depend on translated wording. Language adherence remains part of the agent's substantive self-check, not a claim of automated language certification.

Criteria are parsed into a canonical `criteria.json` in each job. Explicit IDs such as `C01` define assessable entries; document titles and introductions are excluded when structured entries exist. Markdown headings and legacy plain one-criterion-per-line rules are supported. New designs use `## C01 — Short title` followed by detailed Markdown guidance. Existing report files stay immutable; the reader presents real criteria as colored cards and omits historic framework-title assessments.

`web/markdown.js` is the shared safe Markdown renderer, re-exported by `src/markdown.mjs`; `MarkdownView` powers the Review Criteria and Review Playbook previews. `web/markdown.css` supplies common browser/PDF typography. Editing switches to the Markdown source. Generated report tables allow at most two text columns plus up to three narrow categorical estimate columns. Older wide tables are folded into Item/Details presentation without dropping their content or citations.
